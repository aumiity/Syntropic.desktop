ระบบสิทธิ์ตาม Role (เจ้าของร้าน · เภสัชกร · พนักงาน)

เปลี่ยนสิทธิ์จาก "โค้ดฮาร์ดโค้ด" เป็น "ข้อมูลที่ตั้งค่าได้" — มีหน้า Settings เดียวคุมว่าใครทำอะไรได้ 3 สถานะ (ปิด / เปิด / ต้องขออนุมัติ)

ผ่าน audit 2 รอบ 3 เฟส (มี checkpoint) แตะ ~63 จุด gate 2026-06-28

1 ภาพรวม — ทำอะไร ทำไม

ปัญหา: ตอนนี้ "สิทธิ์การใช้งาน" ไม่ใช่ข้อมูล แต่เป็นโค้ด requireAdmin() ที่ฮาร์ดโค้ดกระจายอยู่ ~63 จุดทั่ว electron/ipc/*.ts และมี role แค่ 2 ตัวตายตัว (admin/staff) แก้สิทธิ์ไม่ได้เลย พอฟังก์ชันเริ่มเยอะ การคุมว่าใครทำอะไรได้เลยกระจัดกระจายและขยายยาก

แผนนี้แก้โดย: เพิ่ม role ตรงกลาง (เภสัชกร) เป็น 3 role, ย้ายสิทธิ์ทั้งหมดมาเก็บเป็นข้อมูลในตาราง role_permissions, สร้างชั้นบังคับสิทธิ์ตัวใหม่ requirePermission() แทน requireAdmin(), แล้วทำหน้า Settings เมทริกซ์ให้เจ้าของร้านเปิด/ปิดสิทธิ์ของแต่ละ role ได้เอง

เสร็จแล้วได้: เจ้าของร้านกำหนดเองได้ว่าเภสัชกร/พนักงาน ทำอะไรได้บ้าง แต่ละสิทธิ์เลือกได้ 3 สถานะ — ปิด (ทำไม่ได้), เปิด (ทำได้เลย), ต้องขออนุมัติ (ทำได้ถ้ามีคนสิทธิ์สูงกว่ามากดยืนยัน)

ทุกการกระทำที่มีสิทธิ์ ไหลผ่าน 3 ชั้น: หน้าจอ (ซ่อนปุ่ม = UX) → IPC ฝั่ง main (ด่านจริง) → ตารางสิทธิ์ + registry. ด่านจริงคือ requirePermission() ตัดสินจาก 3 สถานะ:

เจ้าของร้าน (owner) ผ่านทุกด่านอัตโนมัติ ไม่เก็บใน DB. หน้าจอเป็นแค่ UX — ความปลอดภัยจริงอยู่ที่ requirePermission ฝั่ง main เสมอ.

3 ก่อน ↔ หลัง

ก่อน

  • role ตายตัว 2 ตัว: admin / staff
  • สิทธิ์ฮาร์ดโค้ดด้วย requireAdmin() ~63 จุด แก้ไม่ได้
  • staff ทำงานพิเศษได้เฉพาะ 4 อย่าง (ผ่าน manager override ที่ฝังในโค้ด)
  • อยากเปลี่ยน "ใครทำอะไรได้" = ต้องแก้โค้ด

หลัง

  • 3 role: เจ้าของร้าน / เภสัชกร / พนักงาน
  • สิทธิ์เป็นข้อมูลในตาราง role_permissions ปรับผ่านหน้า Settings
  • ทุกสิทธิ์ "การกระทำ" ตั้งเป็น "ต้องขออนุมัติ" ได้ (ขยายแนวคิด override ให้ครบ)
  • เจ้าของร้านเปลี่ยนสิทธิ์เองได้ ไม่ต้องแก้โค้ด

4 ส่งผลอย่างไร

ข้อดี

  • คุมสิทธิ์รวมศูนย์ที่เดียว — เลิกตามแก้โค้ดกระจาย
  • มี role เภสัชกรเป็นมือขวา (เห็นต้นทุน/รายงาน/แก้ราคา/ปรับสต็อกได้ โดยไม่ต้องเป็นเจ้าของร้าน)
  • workflow "ขออนุมัติ" ยืดหยุ่นขึ้น — ใครก็ตามที่ role อนุญาตสิทธิ์นั้น อนุมัติได้ (ไม่จำกัดเจ้าของร้าน)
  • fail-safe: คีย์แปลกปลอม/ค่าพัง = ปฏิเสธไว้ก่อน

ข้อเสีย / ต้นทุน

  • งานใหญ่: แตะ ~63 จุด gate + หลาย layer (จึงแบ่ง 3 เฟส มี checkpoint)
  • สิทธิ์ฝั่งหน้าจอถูก snapshot ตอน login — แก้เมทริกซ์แล้ว ผู้ที่ login ค้างต้อง login ใหม่จึงเห็นผล (ข้อจำกัดที่ยอมรับได้)

ข้อควรระวัง

  • schema.ts:1095 base='admin' = username ของเจ้าของร้าน ไม่ใช่ role → ห้ามเปลี่ยน; seed.ts:78 มี 'admin' สองตัว เปลี่ยนแค่ตัวหลัง (role) ตัวแรก (password) ห้ามแตะ
  • จุดเทียบ role === 'admin' กระจายทั้ง main+renderer — ต้องไล่เปลี่ยนเป็น 'owner' ให้ครบ (รวม key ในออบเจ็กต์ที่ grep จับยาก เช่น ROLE_LABEL)
  • กันเจ้าของร้านล็อกตัวเอง: ล็อกช่อง role ในฟอร์ม + guard ฝั่ง main (ห้าม demote/disable บัญชี owner ที่ผูกอีเมล)
  • invariant allow-list payload: permissions:save เขียนจากชุดคีย์ที่ validate แล้ว ไม่ spread ดิบ

5 UX / UI

แท็บใหม่ใต้ ตั้งค่า ชื่อ "สิทธิ์การใช้งาน" (เห็นเฉพาะเจ้าของร้าน) เป็นตารางเมทริกซ์: แถว = สิทธิ์ (จัดกลุ่ม), คอลัมน์ = เจ้าของร้าน · เภสัชกร · พนักงาน

  • คอลัมน์เจ้าของร้าน = ติ๊กเต็มทุกแถว ปิดการแก้ (เทา)
  • ช่องเภสัชกร/พนักงาน: สิทธิ์ "การกระทำ" = dropdown 3 ค่า (ปิด/เปิด/ต้องขออนุมัติ); สิทธิ์ "ดู" = 2 ค่า (ปิด/เปิด)
  • บันทึกแบบ explicit — ปุ่ม "บันทึก" + "ยกเลิก" (ไม่ auto-save) ตาม convention dropdown/checkbox ของแอป
  • กล่อง manager-override เดิม เปลี่ยนข้อความเป็น "ต้องขออนุมัติ / ผู้อนุมัติ" และโหลดรายชื่อผู้มีสิทธิ์อนุมัติตามสิทธิ์นั้น

ยึดตาม /theme: bar h-12 / control h-9, semantic token เท่านั้น, ไม่มี emoji, ใช้ src/components/ui/* ล้วน, ไม่เพิ่ม primitive ใหม่ (ใช้ Select/Table เดิม → ไม่ต้องแก้ showcase)

Definition of done

  • 3 fixed roles: owner (full+locked), pharmacist, staff.
  • Per (role × permission) state in DB role_permissions, state ∈ off|allow|override.
  • Owner-only Settings tab "สิทธิ์การใช้งาน" edits the matrix (explicit save).
  • All ~63 requireAdmin sites replaced by requirePermission(e,key,override?); renderer uses useCan(key) (UX only).
  • tsc passes; grep requireAdmin( → 0 in electron/ipc after Phase 2; matrix toggles change behavior per role; owner can never lock self out of permission.manage (renderer lock + main guard).
