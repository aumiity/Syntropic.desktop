แยกรหัสไปรษณีย์ออกจากที่อยู่ร้าน

เพิ่มฟิลด์ shop_postcode แยกจาก shop_address — ฉลากยาดึงที่อยู่โดยไม่มีรหัส ปณ. ติดมา ส่วนใบเสร็จ/ใบกำกับภาษี/GR ยังแสดงรหัสได้ตามปกติ

ผ่าน audit 2 รอบ — execute-ready ขอบเขต: schema + IPC + 5 จุด UI/เอกสาร 2026-06-20

1 ภาพรวม — ทำอะไร ทำไม

ปัญหา: ตอนนี้รหัสไปรษณีย์ถูกพิมพ์รวมอยู่ในช่อง "ที่อยู่ร้าน" (settings.shop_address) ช่องเดียว พอเอาที่อยู่ไปขึ้นฉลากยา รหัส ปณ. ก็ติดไปด้วย ทำให้บรรทัดที่อยู่บนสติกเกอร์ยาวเกินจนเบียดพื้นที่ส่วนอื่น

วิธีแก้: แยกรหัสไปรษณีย์ออกเป็นฟิลด์ของตัวเอง (settings.shop_postcode) ฉลากยาจะดึงเฉพาะ shop_address (ไม่อ่านรหัส ปณ. เลย → ไม่ต้องแก้โค้ดฉลากแม้แต่บรรทัดเดียว) ส่วนใบเสร็จ/ใบกำกับภาษี/ใบรับของ (GR) จะเอา shop_address + shop_postcode มาต่อกันในบรรทัดเดียว → ยังเห็นรหัสครบเหมือนเดิม

เสร็จแล้วได้อะไร: ฉลากยาสั้นลง สะอาดขึ้น เอกสารทางการยังครบถ้วน และรหัส ปณ. กลายเป็นข้อมูลที่จัดการแยกได้ชัดเจนในหน้าตั้งค่าร้าน

3 ก่อน ↔ หลัง

ก่อน

  • ที่อยู่ + รหัส ปณ. รวมในช่องเดียว shop_address
  • ฉลากยา: 123 ถ.สุขุมวิท กรุงเทพฯ 10110 — บรรทัดยาวเบียดพื้นที่
  • ใบเสร็จ/ใบกำกับ: แสดงรหัสได้ (เพราะฝังในที่อยู่)
  • ไม่มีทางเอารหัสออกจากฉลากโดยไม่กระทบเอกสารอื่น

หลัง

  • ที่อยู่อยู่ shop_address, รหัสอยู่ shop_postcode แยกกัน
  • ฉลากยา: 123 ถ.สุขุมวิท กรุงเทพฯ — สั้น สะอาด ไม่มีรหัส
  • ใบเสร็จ/ใบกำกับ/GR: 123 ถ.สุขุมวิท กรุงเทพฯ 10110 — ต่อรหัสกลับ
  • หน้าตั้งค่าร้านมีช่อง "รหัสไปรษณีย์" แยกชัดเจน

4 ส่งผลอย่างไร

ข้อดี

  • ฉลากยาบรรทัดที่อยู่สั้นลง ไม่มีรหัส ปณ. มากวนพื้นที่
  • โค้ดฉลากไม่ต้องแก้เลย — แค่ไม่อ่านฟิลด์ใหม่ รหัสก็หายเอง
  • เอกสารทางการยังครบ (ต่อรหัสกลับแบบ space-join บรรทัดเดียว)
  • แก้ Setting type ที่เดียว ไหลถึง consumer ทั้ง 3 (Partial<Setting>)
  • migration idempotent — ฐานข้อมูลเดิมได้คอลัมน์ใหม่ไม่กระทบข้อมูล

ข้อเสีย / ต้นทุน

  • ต้องกรอกรหัส ปณ. ใหม่เองที่หน้า ShopTab หนึ่งครั้ง (ย้ายออกจากช่องที่อยู่เดิม)
  • แตะ schema + IPC → ต้องผ่าน tsc + click-test ในแอปจริง

ข้อควรระวัง

  • Allow-list invariant: saveShop UPDATE สร้าง SQL จาก Object.keys — คอลัมน์ shop_postcode ต้องมีอยู่ใน DB ก่อนฟอร์มส่งค่ามา ไม่งั้น throw no such column (จึงทำ schema ก่อนเป็นสเต็ปแรก และ ship พร้อมกัน)
  • สถานะช่วงเปลี่ยนผ่าน: ก่อนพี่ย้ายรหัสออกจากช่องที่อยู่ ฉลากจะยังโชว์รหัสเดิม (เพราะยังฝังใน shop_address) และเอกสารจะโชว์รหัสครั้งเดียว (ฟิลด์ใหม่ว่าง = ต่อแล้วไม่มีอะไร) — ไม่มีรหัสซ้ำ ไม่ crash เป็นสภาพที่คาดไว้ตามการ migrate แบบ manual
  • ห้ามแก้ไฟล์ electron/**/*.js (artifact เก่า) — แก้แค่ .ts
  • text-size ขั้นต่ำ text-xs, ใช้ ui-primitive (ห้าม raw HTML), ไม่มี emoji ในข้อความ UI

5 UX / UI

ShopTab (ตั้งค่า > ข้อมูลร้าน): เพิ่ม FormField "รหัสไปรษณีย์" เป็นช่องครึ่งแถว วางใต้ช่องที่อยู่ จับคู่กับช่องโทรศัพท์ — กริดไหลเป็น [รหัสไปรษณีย์ | โทรศัพท์], [LINE ID | เลขใบอนุญาต], [เลขผู้เสียภาษี | สาขา] ใต้ช่องมีข้อความบอกใบ้สีจาง (text-xs text-muted-foreground): "แยกจากที่อยู่ — รหัสนี้จะไม่แสดงบนฉลากยา แต่จะแสดงในใบเสร็จ/ใบกำกับภาษี" ใช้ <Input variant="elevated"> ตามสไตล์เดิมของไฟล์

SetupWizard (ตั้งค่าครั้งแรก): เพิ่มช่อง "รหัสไปรษณีย์ (ไม่บังคับ)" ใกล้ช่องที่อยู่ ใช้ <Input> เปล่า (default = elevated) ไม่บังคับกรอก (ไม่อยู่ใน validate()) — ทุกอย่างเป็นภาษาไทย ตาม pattern /theme เดิม ไม่มีปุ่ม/สีบทบาทใหม่

B แผนปฏิบัติงาน (Claude อ่านส่วนนี้แล้วลงมือ)

Definition of done

  • Column settings.shop_postcode TEXT NOT NULL DEFAULT '' exists (CREATE + ALTER migration).
  • Setting type carries shop_postcode?: string.
  • ShopTab has a "รหัสไปรษณีย์" input that loads + saves; persists across reload.
  • SetupWizard has an optional "รหัสไปรษณีย์" input wired into settings:completeSetup.
  • Drug label renders the address with NO postcode (zero label code changes).
  • Receipt slip, tax invoice, GR each render shop_address + shop_postcode (space-joined).
  • npx tsc --noEmit -p tsconfig.json shows ONLY the pre-existing unrelated error in src/pages/Theme/index.tsx (no new errors).

Build-pipeline fact

  • vite-plugin-electron bundles electron/main.ts → gitignored dist-electron/ at dev time. Committed electron/**/*.js are STALE artifacts (see vite.config.ts comment). Edit ONLY the .ts sources — never the .js.
