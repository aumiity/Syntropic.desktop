Full Program Audit

ตรวจสุขภาพทั้งโปรแกรม 4 มิติ (เงิน-สต็อก / ความปลอดภัย / คุณภาพโค้ด / UI) แบ่งเป็น 11 รอบ — รายงานก่อน ค่อยเลือกแก้ — เพื่อเตรียม production-ready

ผ่าน audit แผน 2 รอบ PARKED — รอหลังงาน VAT 11 รอบ (R0–R10) · ~7-8 เซสชัน 2026-06-10

1 ภาพรวม — ทำอะไร ทำไม

แอปโตมาถึง ~45,000 บรรทัด (renderer ~35K + Electron main ~9.4K, IPC 16 โมดูล) และกำลังจะเข้าใช้งานจริงที่ร้าน + import ข้อมูล Hygeia จริง — แต่ยังไม่เคยมีการกวาดตรวจทั้งระบบสักครั้ง บั๊กเงิน/สต็อกหรือช่องโหว่ role ที่หลุดไป production จะแพงกว่าตอนนี้มาก

แผนนี้แบ่งการตรวจเป็น 11 รอบ: backend ตรวจตามมิติ (เงิน → สต็อก → security → คุณภาพโค้ด เพราะ logic ข้ามโมดูล) / UI ตรวจตามหน้า (เพราะกฏ design เป็นรายหน้า) — แต่ละรอบส่ง sub-agents ขนานกัน 2-3 ตัว แล้ว orchestrator รวบรวม+ยืนยัน findings เอง

กติกาหลัก: รอบตรวจไม่แก้โค้ดเลย ทุกอย่างออกเป็นรายงานจัด severity (P0-P3) ที่ docs/audits/full-program/ แล้วพี่เลือกเองว่าแก้ตัวไหน · จุดเสี่ยงสูง (เงิน/สต็อก) มี runtime scenario รันบนแอปจริงด้วย — บน DB สำเนาชั่วคราวเท่านั้น

3 ก่อน ↔ หลัง

ก่อน

  • ไม่รู้ว่าระบบ "พร้อม production แค่ไหน" — ความมั่นใจมาจาก click-test รายฟีเจอร์เท่านั้น
  • กฏ HARD invariant เคยตรวจเฉพาะตอนเขียนของใหม่ ไม่เคยกวาดย้อนทั้งระบบ
  • ช่องโหว่ role/allow-list อาจหลบอยู่ใน handler เก่าที่เขียนก่อนมีระบบ login
  • บั๊กเงิน/สต็อกถ้ามี จะไปโผล่ตอนใช้จริงกับข้อมูลร้านจริง

หลัง

  • มี MASTER.md สรุป findings ทั้งระบบ จัด severity P0-P3 + นับยอดต่อรอบ
  • จุดเงิน/สต็อกผ่าน runtime scenario จริง มีบันทึก PASS/FAIL เป็นหลักฐาน
  • ได้ shortlist "ควรแก้ก่อนเปิดร้าน" (P0 ทั้งหมด + P1 คัดแล้ว) ให้พี่ตัดสินใจ
  • ของที่ track อยู่แล้ว (tokenization ฯลฯ) ถูก tag แยก ไม่ปนกับบั๊กใหม่

4 ส่งผลอย่างไร

ข้อดี

  • เห็นความเสี่ยงทั้งระบบในรายงานเดียว ก่อนเงินจริง/ข้อมูลจริงเข้า
  • report-only → ไม่มี diff ใหญ่ ไม่มีความเสี่ยง regression ระหว่างตรวจ
  • แบ่งรอบจบในตัว — หยุด/สลับกับงานอื่นได้ทุกจุด ไม่ค้างกลางทาง
  • agents ขนาน + checklist กลาง → เร็วและมาตรฐานเดียวกันทุกหน้า

ข้อเสีย / ต้นทุน

  • ใช้เวลา ~7-8 เซสชัน + ค่า token ของ agents ขนานหลายตัว
  • findings UI บางส่วนจะซ้ำกับ backlog เดิม (กันด้วย tag KNOWN-TRACKED แล้ว)
  • รายงานเสร็จยังไม่ได้แปลว่าแก้เสร็จ — งานแก้เป็นเฟสถัดไปที่พี่เลือกเอง

ข้อควรระวัง

  • Runtime scenario ห้ามแตะ DB จริงเด็ดขาด — ต้องทำตาม R0 ขั้น 1-5 ครบ (สำเนา 3 ไฟล์ลง database/ + ทำหมัน backup + marker [AUDIT-TMP])
  • npm run dev จะเด้งหน้าต่าง Electron บน DB จริงขึ้นมาเอง — ต้องปิดทิ้งทันที ใช้เฉพาะหน้าต่างจากเทอร์มินัล 2 ที่มี marker
  • ห้าม npm install ตลอดการ audit (พัง better-sqlite3)
  • agents รายงานอย่างเดียว ห้ามแก้ไฟล์ — ถ้า agent เผลอแก้ ให้ revert ทันที

5 UX / UI

แผนนี้ไม่เปลี่ยน UI ใด ๆ (ตรวจอย่างเดียว) — รอบ R5-R9 ใช้ checklist กลาง 10 ข้อจากกฏ HARD ใน CLAUDE.md + docs/claude/ui-*.md: bar h-12/control h-9 · semantic tokens · ห้าม raw HTML/local helper · text-size hierarchy · ห้าม emoji · modal contract + ปุ่ม footer ตาม role · icon size-N · table-card 4 โซน · truncate กับวรรณยุกต์ไทย · ห้าม tabular-nums — ผลตรวจ UI จะกลายเป็นวัตถุดิบให้ UI Redesign Pass ที่ทำอยู่ด้วย
