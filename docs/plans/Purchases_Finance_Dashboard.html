Purchases Finance Dashboard

เพิ่มแผงภาพรวมการเงินฝั่งซื้อ (admin) ที่หน้า Manage › ประวัติการซื้อ ให้สอดคล้องกับหน้า Sales — staff ใช้หน้าเดิมทุกอย่าง

ผ่าน audit 2 รอบ — ไม่มี P0/P1 ค้าง Layout A · มิเรอร์ Sales renderer + backend 1 บรรทัด 2026-06-28

1 ภาพรวม — ทำอะไร ทำไม

วันนี้หน้า ประวัติการขาย มีแผงภาพรวมการเงินสำหรับ admin (การ์ดสรุป + กราฟแนวโน้ม + การ์ดสถานะ/สรุป) แต่หน้า ประวัติการซื้อ ยังมีแค่ตารางประวัติเปล่า ๆ — admin ต้องเดาภาพรวมเอาเองว่าช่วงนี้ซื้อไปเท่าไหร่ จ่ายสดเท่าไหร่ ติดเครดิตเท่าไหร่ และยังค้างจ่ายเจ้าหนี้อยู่เท่าไหร่

แผนนี้เพิ่ม dashboard ภาพรวมการซื้อ (เฉพาะ admin) ที่หน้า src/pages/Manage/Purchases.tsx โดยลอกโครงจากหน้า Sales เป๊ะ ๆ แต่เปลี่ยนเนื้อหาเป็นมุมมองการซื้อ ข้อมูลทั้งหมดดึงจาก IPC ที่มีอยู่แล้ว (reports.financeSummary + reports.salesPurchaseTrend) ซึ่ง requirePermission('report.finance') อยู่แล้ว → staff มองไม่เห็นแผงนี้เลย และหน้าของ staff คงเดิมทุกพิกเซล

แตะ backend แค่ 1 บรรทัด (เพิ่ม COUNT(*) AS purchase_count ต่อช่วงเวลาในกราฟ) เพื่อให้กราฟสลับดู "ยอดซื้อ / จำนวนบิล" ได้ — เป็นการเพิ่มฟิลด์แบบ backward-compatible ไม่กระทบหน้า Sales/Dashboard ที่ใช้ IPC ตัวเดียวกัน

2 โครงสร้าง / แผนผัง

การไหลของข้อมูล: หน้าจอ Purchases (admin) ยิง IPC 2 ตัวตามช่วงวันที่ของ MultiDatePicker → main process รวมยอดจากตาราง SQLite → ส่งกลับมาวาดเป็น MetricStrip + กราฟ + การ์ดสถานะ/สรุป

3 ก่อน ↔ หลัง

ก่อน

  • admin: หน้าประวัติการซื้อ = ตารางเปล่า + การ์ดนับจำนวน 5 ใบใน slot บน
  • ไม่มีภาพรวมยอดเงิน/แนวโน้ม/เจ้าหนี้คงค้าง — ต้องเปิดหน้า Finance แยก
  • หน้าไม่เลื่อน (ตารางสูงเต็มจอ)

หลัง

  • admin: เห็นแผงภาพรวมการเงินด้านบน (เหมือนหน้า Sales) แล้วตามด้วยตารางประวัติ สูง h-[34rem] เลื่อนในตัว
  • เห็นยอดซื้อ/สด/เครดิต/ค้างชำระ + แนวโน้ม + สัดส่วนสถานะ ในที่เดียว
  • ทั้งหน้าเลื่อนรวมกัน (การ์ด + กราฟ + ตาราง)
  • staff: เหมือนเดิมทุกพิกเซล — การ์ดนับ 5 ใบ + ตารางเต็มจอ

4 ส่งผลอย่างไร

ข้อดี

  • admin เห็นสุขภาพการซื้อ/กระแสเงินสด/เจ้าหนี้คงค้างทันที โดยไม่ต้องสลับหน้า
  • เลย์เอาต์เดียวกับ Sales → สลับแท็บแล้วไม่ต้องเรียนรู้ใหม่
  • reuse สูง: ใช้ IPC/คอมโพเนนต์เดิมเกือบทั้งหมด, ดึง 4 ฟังก์ชัน pure ออกเป็น lib ร่วม (ลดโค้ดซ้ำ)
  • backend เพิ่มแค่ 1 ฟิลด์ backward-compatible — Sales/Dashboard ไม่กระทบ

ข้อเสีย / ต้นทุน

  • เพิ่มการ fetch 2 ครั้งต่อการเปลี่ยนช่วงวันที่ (เฉพาะ admin) — เบา เพราะเป็น aggregate query
  • render-helper statusCard/summaryCard ถูกลอกมาไว้ในไฟล์ Purchases (ตามแบบ Sales) — โค้ดซ้ำเล็กน้อย รอ extract เป็น shared component ในอนาคต

ข้อควรระวัง

  • invariant ห้ามแตะ experience ของ staff — ทุกอย่าง gate ด้วย isAdmin/canFinancePanel
  • invariant hooks ต้องเรียกไม่มีเงื่อนไข (hoist เหนือ early-return) — กันจอขาวตอนสลับ role
  • invariant font-relative: ใช้ rem (h-[34rem], h-[9.1rem]) ห้าม hardcode px ชดเชย
  • toast ของ Purchases เป็นแบบ positional toast(msg, 'error') ไม่ใช่ object เหมือน Sales
  • ดึง 4 ฟังก์ชันออกจาก Sales → ต้องลบ import dayjs + type Granularity ที่กลายเป็น orphan

5 UX / UI

  • เฉพาะ admin (role ที่ useCan('report.finance') !== 'off'): แผงภาพรวมแสดงตลอด ไม่มีปุ่มพับ/กาง ทั้งหน้าเลื่อนรวมกัน — ตารางประวัติสูงตายตัว h-[34rem] (~10 แถว) เลื่อนในตัว
  • staff: หน้าเดิม — การ์ดนับ 5 ใบใน slot บน + ตารางเต็มจอ
  • ตัวเลขใน MetricStrip อิงช่วงวันที่อย่างเดียว (จาก MultiDatePicker) ไม่ผูกช่องค้นหา/ตัวกรองของตาราง — ตรงตามเจตนาแผง Finance ของ Sales
  • กราฟใช้ TrendChart variant="bar" + segmented Tabs สลับ "ยอดซื้อ / จำนวนบิล"; granularity อิง dateMode (วัน→ชม., เดือน→วัน, ปี→เดือน)
  • สีทั้งหมดใช้ semantic token (hsl(var(--primary)) ฯลฯ) ไม่มี palette literal, ไม่มี emoji, ไม่มี raw HTML — ใช้ MetricStrip/SectionCard/TrendChart จาก src/components/ui/
  • โทนสีการ์ดสถานะตั้งใจให้ตรงกับ MetricStrip ที่อยู่เหนือมัน (เงินสด=success, เครดิต=info, ค้างชำระ=amber, ยกเลิก=destructive) ไม่ใช่ตาม badge ในตาราง
  • headline delta ใช้ { invert: true } แบบต้นทุน (ซื้อเพิ่ม = แดงเตือน) เหมือนการ์ด "ต้นทุนรวม" ของ Sales — ปรับให้ขึ้น=เขียวได้ง่ายโดยถอด arg นี้
