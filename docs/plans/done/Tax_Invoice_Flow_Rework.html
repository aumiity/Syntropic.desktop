คิด flow การพิมพ์ใบกำกับภาษีใหม่ (v2)

ผู้ซื้อบนใบกำกับ = ลูกค้าที่ผูกกับบิลเท่านั้น · เปลี่ยนผู้ซื้อด้วยการแก้ลูกค้าของบิล · พิมพ์ตัวจริงแล้วล็อกบิล

v2 · รื้อจาก v1 (picker ใน modal) VAT / ใบกำกับภาษี 2026-06-12

1 ภาพรวม — ทำอะไร ทำไม

ปัญหาของ v1 (ที่ต้องรื้อ): กล่องพิมพ์ใบกำกับภาษีมี "ปุ่มเลือกลูกค้าจากระบบ" + ช่องพิมพ์ผู้ซื้ออิสระ — แปลว่า บิลที่คิดเงินไปแล้วจะออกใบกำกับให้ใครก็ได้ ผู้ซื้อบนใบหลุดจากลูกค้าจริงของบิล เปิดช่องโหว่ทางบัญชี/ภาษี

หลักการใหม่ (v2):

  • ผู้ซื้อบนใบกำกับ = ลูกค้าที่ผูกกับบิลนั้นเท่านั้น (อ่านจาก sales.customer_id → customer record) — กล่องพิมพ์เป็น read-only ไม่มี picker ไม่มีช่องพิมพ์อิสระ
  • จะเปลี่ยนผู้ซื้อ ต้องแก้ "ลูกค้าของบิล" (reassign customer_id) ผ่านปุ่ม "แก้ไขรายชื่อลูกค้า" ใน SaleDetailDialog (สิทธิ์ admin)
  • พิมพ์ใบกำกับ "ตัวจริง" แล้ว = ล็อกบิล — แก้ลูกค้าไม่ได้, ยกเลิกบิลไม่ได้, พิมพ์ได้แค่ "สำเนา"
  • รวมทุก action ไว้ที่ SaleDetailDialog ที่เดียว — ตารางรายการขายเหลือแค่ ดูรายละเอียด/พิมพ์ใบเสร็จ/ยกเลิกบิล

VAT ย้อนหลังยังเหมือนเดิม: บิลที่ขายแบบ "ไม่เอา VAT" (total_vat = 0) ไม่แปลงย้อนหลัง — ออกใบกำกับได้เฉพาะบิล total_vat > 0

2 โครงสร้าง / แผนผัง

SaleDetailDialog เป็นศูนย์กลาง — เปิดได้จากตารางรายการขายและรายงานภาษีขาย แล้วแตกเป็น 3 action (แก้ลูกค้า / ออก-สำเนาใบกำกับ / ยกเลิกบิล) โดยมีกฎ "ล็อก" คุมทั้ง 3:

เส้นส้ม = เส้นทางหลัก (ออก/พิมพ์ใบกำกับ) · เส้นแดงประ = กฎล็อก (พิมพ์ตัวจริง → ยกเลิก/แก้ลูกค้าโดน reject) · กล่องเส้นประ = ชั้นข้อมูล (IPC/DB)

3 ก่อน ↔ หลัง

ก่อน (v1)

  • กล่องพิมพ์มี picker เลือกลูกค้า + ช่องพิมพ์ผู้ซื้ออิสระ → ออกใบให้ใครก็ได้
  • ปุ่มออกใบกำกับกระจายทั้งใน Manage/Sales kebab และ SaleDetailDialog
  • พิมพ์ใบกำกับตัวจริงแล้วยัง ยกเลิกบิลได้ / แก้ผู้ซื้อได้
  • SaleDetailDialog ไม่โชว์ยอดแยก VAT (มีแค่ยอดสุทธิ/ทุน/กำไร)
  • มี write-back เขียน id_card กลับจากกล่องพิมพ์

หลัง (v2)

  • กล่องพิมพ์ read-only — ผู้ซื้อมาจากลูกค้าของบิลเท่านั้น
  • ทุก action รวมที่ SaleDetailDialog; ตารางเหลือ ดูรายละเอียด/พิมพ์ใบเสร็จ/ยกเลิก
  • พิมพ์ตัวจริงแล้ว = ล็อก (แก้ลูกค้า+ยกเลิกถูกปิด, พิมพ์ได้แค่สำเนา) บังคับ 2 ชั้น
  • SaleDetailDialog โชว์ มูลค่าก่อนภาษี / VAT / รวมสุทธิ ครบ
  • เปลี่ยนผู้ซื้อ = "แก้ไขรายชื่อลูกค้า" (admin) reassign ทั้งบิล

4 ส่งผลอย่างไร

ข้อดี

  • ใบกำกับผูกกับลูกค้าจริงของบิลเสมอ — ปิดช่องโหว่ "ออกให้ใครก็ได้"
  • พิมพ์ตัวจริงแล้วล็อกแน่น (UI + backend) — กันแก้ย้อนหลังเอกสารภาษี
  • flow รวมที่เดียว เข้าใจง่าย ไม่ต้องไล่หลายเมนู
  • เห็นยอด VAT ในบิลชัดเจน

ข้อเสีย / ต้นทุน

  • ถ้าลูกค้าของบิลข้อมูลไม่ครบ (ไม่มีที่อยู่/เลขภาษี) ต้องไปเติมที่ "แก้ไขลูกค้า" (People) ก่อน แล้วค่อยออกใบ
  • เพิ่ม handler + query ขึ้นเล็กน้อย (join/subquery tax_invoices)
  • ต้อง revert งาน v1 บางส่วน (picker/write-back/handler)

ข้อควรระวัง (invariant)

  • ล็อกหลัง "พิมพ์สำเร็จ" ไม่ใช่ "กดออก" (P0 จาก audit): เดิม tax:issueOrGet ตั้ง original_printed=1 ทันทีที่ INSERT → ถ้า dialog พิมพ์ถูกยกเลิก/พลาด บิลจะ ล็อกถาวร (ยกเลิก/แก้ลูกค้าไม่ได้) ทั้งที่ยังไม่ได้พิมพ์จริง. v2 เลื่อน flag: issueOrGet INSERT ด้วย original_printed=0 (แค่ snapshot buyer) → renderer พิมพ์สำเร็จ (ต้นฉบับ) ค่อยเรียก tax:confirmOriginalPrinted ตั้ง=1 = ล็อก. ตรงเจตนา "พิมพ์ไปแล้วค่อยล็อก"
  • Allow-list payload: updateSaleCustomer เขียนเฉพาะ customer_id (+เคลียร์ name_free) ระบุชัด ไม่ spread
  • Walk-in C0000: picker reassign ปิด walk-in; handler reject ถ้า customer_id = walkInCustomerId (กัน NULL/แทนค่า C0000 ตามกฎ)
  • ล็อก 2 ชั้น: UI ซ่อน/disable + backend reject ทั้ง updateSaleCustomer และ voidSale — UI อย่างเดียวไม่พอ
  • snapshot 0 ระหว่างทาง: ถ้าพิมพ์พลาด เหลือแถว tax_invoices original_printed=0 (ยังไม่ล็อก) แก้ลูกค้าได้ปกติ; issueOrGet จะ UPDATE buyer ทับจากลูกค้าใหม่ตอนพิมพ์รอบหน้า — snapshot heal เอง
  • บิลเก่าจาก v1 (deploy): tax_invoices ที่ออกสมัย v1 มี original_printed=1 อยู่แล้ว → หลัง deploy จะ ล็อกทันที (ยกเลิก/แก้ลูกค้าไม่ได้) — เป็นพฤติกรรมที่ตั้งใจ (v1 issue=print) ไม่มี unlock path (รับทราบโดยตั้งใจ ไม่ต้องทำ escape hatch)
  • reassign = ขยับรายงาน retroactive: updateSaleCustomer เปลี่ยน customer_id ของบิลย้อนหลัง → บิลย้ายเข้า/ออก ประวัติลูกค้าใน report ที่ join customers (salesList/vatSummary/สถิติลูกค้าใหม่-เก่า) — เป็น semantic ที่ถูกต้อง (แก้ผู้ซื้อให้ตรง) แต่ต้องรู้ว่ามีผล. สต็อก/FEFO ไม่กระทบ
  • reports:getSale (by id) ไม่แตะโดยตั้งใจ — ไม่มีใครใช้ดึง lock/tax ในแผนนี้ (SaleDetailDialog ใช้ getSaleByInvoice)
  • สิทธิ์: แก้ลูกค้า = requireAdmin(_e, override) + useManagerOverride ฝั่ง renderer (เหมือน voidSale)
  • สำเนาใช้ snapshot เดิม: บิลที่ออกแล้ว buyer มาจาก tax_invoices (snapshot ตามกฎหมาย) ไม่ re-pull จากลูกค้าที่อาจถูกแก้
  • แก้เฉพาะไฟล์ .ts/.tsx — electron/ipc/*.js ที่ track เป็น artifact เก่า ไม่ใช่ runtime
