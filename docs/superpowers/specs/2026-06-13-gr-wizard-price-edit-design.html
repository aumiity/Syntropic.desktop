Design Spec · หน้ารับสินค้า (GR)

แก้ราคาทุกหน่วยใน GR Wizard
+ อุดรอยประวัติราคา + แจ้งเตือนทุนเปลี่ยน

● APPROVED (design) 2026-06-13 รอเขียนแผน implementation 2 เฟส

1 ปัญหาที่จะแก้

ตอนนี้การตั้งราคาขายในหน้ารับสินค้ามี “รอยรั่ว” เรื่องประวัติ และพฤติกรรมไม่สม่ำเสมอ

ทางที่เปลี่ยนราคาขายสถานะบันทึกประวัติ?ขออนุญาต admin?
Wizard step 4 → purchase.save
เขียนทับ price_retail ตอนบันทึกใบรับ		 ใช้งานจริง ✗ ไม่บันทึก ✗ ไม่ขอ
Modal ปรับราคาในตาราง
openPriceModal เรียก updatePrice		 สร้างครบ แต่ไม่มีปุ่มเรียก = กำพร้า ✓ บันทึก ✓ ขอ

สรุป: ทางที่ ใช้จริง (wizard) คือทางที่ รั่ว — ส่วนทางที่ทำถูก (modal) กลับถูกทิ้งไม่ได้ต่อปุ่ม และยังมี CSV import เป็นอีกทางเข้าหนึ่ง (ไม่มีราคาขาย) แต่ row จาก CSV เปิดแก้ผ่าน wizard ได้ → การแก้ราคา “ใน wizard” จึงครอบคลุมทั้งสองทางอยู่แล้ว

2 สิ่งที่ต้องการ

ยืนยันกับเจ้าของแล้วทั้ง 6 ข้อ

R1แก้ราคา ใน wizard เป็นหลัก (ครอบคลุมทั้ง row จาก wizard และ CSV) — ไม่ทำ modal แยกที่ตาราง
R2เพิ่ม แจ้งเตือนทุนเปลี่ยน ใน wizard → ผู้ใช้เห็นว่าทุนต่างจากเดิม แล้วตัดสินใจแก้ราคาเอง
R3แก้ราคาใน wizard ได้ ทุกหน่วย (ฐาน + กล่อง/แพ็ค) รวมราคาส่ง (ws1/ws2)
R4admin เท่านั้นแก้ราคาได้ — พนักงานเจอช่องล็อก + ปุ่มขอรหัส admin (สิทธิ์ละเอียดทำทีหลัง)
R5ประวัติราคาเก็บ เฉพาะหน่วยฐาน เหมือนเดิม — หน่วยอื่นไม่เก็บ → ไม่ต้องแตะ schema
R6อุดรอย: purchase.save เลิกเขียนทับ price_retail แบบเงียบ ๆ

3 2 การตัดสินใจสำคัญ

D1 · จังหวะเขียนราคา

เขียนลง DB ทันทีตอนกด “ยืนยัน” ใน step 4

ราคาหลักเปลี่ยนทันที แยกจากการบันทึกใบรับชัดเจน (ตรงกับ pattern modal เดิม). ผลข้างเคียง: ถ้ายกเลิกใบรับทีหลัง ราคาก็เปลี่ยนไปแล้ว — เป็นพฤติกรรมที่ตั้งใจ

D2 · พนักงานไม่ใช่ admin

ช่องราคา read-only + ปุ่ม “ขอสิทธิ์แก้ราคา”

กดปุ่ม → เด้งขอรหัส admin → ผ่าน verifyAdmin แล้วปลดล็อก + เก็บ override ไว้แนบตอนเขียน. รหัสผิด → error ที่ dialog ทันที (ไม่ปล่อยไปพังตอนเขียน)

4 สิ่งที่จะแก้ — Backend

4 จุดในฝั่ง electron

รหัสไฟล์งานloggate
B1purchase.ts ลบ UPDATE products SET price_retail (บรรทัด 229–230) — ปล่อยให้ราคาหลักเป็นของ updatePrice เจ้าเดียว (lot.sell_price ยังเขียนได้ตามเดิม) ——
B2products.ts ใช้ products:updatePrice เดิม สำหรับหน่วยฐาน (retail/ws1/ws2) ✓admin
B3products.ts เพิ่ม updateUnitPrice(productUnitId, {retail,ws1,ws2}, override) — UPDATE product_units ตาม id (เฉพาะ 3 คอลัมน์ราคา, ห้าม spread payload ดิบ) ✗admin
B4auth.ts เพิ่ม auth:verifyAdmin(override) — เช็คสิทธิ์ตอนปลดล็อก (ยังไม่มีในระบบ) —admin

ก่อน (รั่ว)

// purchase.save — ทุกครั้ง
UPDATE products
   SET price_retail = ?
 WHERE id = ?
// ไม่เช็คว่าเปลี่ยนไหม
// ไม่ log · ไม่ขอ admin

หลัง (อุดแล้ว)

// purchase.save: ไม่แตะ price_retail
// ราคาหลัก = ของ updatePrice
//   → log price_logs + admin gate
// lot.sell_price ยังเขียนได้
//   (record ระดับล็อต)

5 สิ่งที่จะแก้ — Wizard step 4

รื้อจาก “ช่องราคาเดียว” เป็น “ราคาขาย ทุกหน่วย” AddProductWizard.tsx

  1. แบนเนอร์แจ้งเตือนทุน (R2) — ถ้าทุนที่กรอก ≠ ทุนเดิม (last_cost_price) → โชว์ “ทุนเปลี่ยน X → Y · ทบทวนราคาขาย” + ตารางเทียบเก่า/ใหม่ (เก็บเกี่ยว layout จาก modal กำพร้า)
  2. ตัวแก้ราคาทุกหน่วย (R3) — ตาราง: แถว = หน่วย (ฐานก่อน) × คอลัมน์ ราคาปลีก / ส่ง1 / ส่ง2 + โชว์กำไร%
  3. Admin gate (R4) —
    admin→แก้ได้เลย
    พนักงาน→ช่องล็อก→ ปุ่ม “ขอสิทธิ์แก้ราคา”→verifyAdmin→ ปลดล็อก + เก็บ override
  4. เขียนตอนยืนยัน row (D1) — กด “ยืนยัน” → เฉพาะหน่วย/ช่องที่เปลี่ยน → ยิง updatePrice(ฐาน) / updateUnitPrice(หน่วยอื่น) แนบ override → แล้วจึง onConfirm(row)

Cleanup

รื้อ dead code modal กำพร้าใน index.tsx: openPriceModal / savePriceModal / closePriceModal + JSX + state ที่เกี่ยว (ตรวจ reference ก่อนลบทุกตัว)

6 แบ่ง 2 เฟส

เฟส 1 ส่งของได้เร็ว (อุดรอยแล้วใช้งานได้จริง) · เฟส 2 เติมให้ครบ R3

① อุดรอย + แจ้งเตือนทุน + admin gate (หน่วยฐาน)
  • B1 ลบรอยรั่ว · B2 ใช้ updatePrice เดิม · B4 เพิ่ม auth:verifyAdmin
  • Wizard step 4: แบนเนอร์ทุน + ตารางเทียบ + ช่องราคาปลีกหน่วยฐาน (โครงช่องเดียวไปก่อน) + admin lock/unlock + เขียนทันที
  • รื้อ dead modal
ได้อะไร: รอยรั่วถูกอุด · มีฟีเจอร์แจ้งเตือนทุน · มี admin gate · ประวัติหน่วยฐานครบ — ใช้งานได้จริง
② ทุกหน่วย + ราคาส่ง (เติมให้ครบ R3)
  • B3 เพิ่ม updateUnitPrice (+ preload + type)
  • Wizard step 4: เปลี่ยนช่องเดียว → ตารางทุกหน่วย × (ปลีก/ส่ง1/ส่ง2); เขียนตอนยืนยันยิง updatePrice(ฐาน) + updateUnitPrice(หน่วยอื่น)
ได้อะไร: ครบ R3 — แก้ได้ทุกหน่วยทุกราคา

7 ข้อควรระวัง

ทุน baseline

เทียบ “ทุนเปลี่ยน” ด้วย last_cost_price (ทุนล่าสุดที่จ่ายจริง) — อย่า fallback ไป weighted-avg cost_price (ของฟรี = 0 ต้องคง 0)

แก้ row ซ้ำ

ตัวเลขใน confirm อาจต่างจากที่ log เล็กน้อย แต่ ประวัติที่บันทึกถูกต้องเสมอ (updatePrice อ่านราคาจริงใน DB)

หน่วยที่รับเข้า ≠ หน่วยขาย — สำคัญตอนเฟส 2

row.units ใน wizard มาจาก purchase_units (หน่วยรับเข้า) แต่ตัวแก้ราคาต้องอิงหน่วย ที่ขายได้ (is_for_sale) — ต้องยืนยันรายการหน่วยใน step 4 ให้เป็นหน่วยขาย ไม่ใช่หน่วยรับเข้าล้วน

allow-list

updateUnitPrice ต้อง UPDATE เฉพาะ 3 คอลัมน์ราคา ห้าม build dynamic SQL จาก payload ดิบ (กฎ HARD)

8 เกณฑ์ตรวจรับ

เฟส 1
  • purchase.save ไม่ UPDATE price_retail อีก
  • บันทึกใบรับที่ไม่แตะราคา → ราคาคงเดิม ไม่มี price_logs เพิ่ม
  • admin แก้ราคาปลีกฐาน → ราคาเปลี่ยน + มีแถว price_logs
  • พนักงาน → ช่องล็อก; รหัสผิดเด้ง error; รหัสถูกปลดล็อก
  • ทุน ≠ เดิม → โชว์แบนเนอร์ + ตารางเทียบ
  • dead modal ถูกรื้อ · tsc ผ่าน
เฟส 2
  • step 4 โชว์ทุกหน่วยขายได้ × (ปลีก/ส่ง1/ส่ง2)
  • แก้หน่วยอื่น → product_units อัปเดต, ไม่มี price_logs
  • แก้หน่วยฐาน (3 price_type) → price_logs เพิ่มตาม type ที่เปลี่ยน
  • admin gate ครอบทุกช่องราคา
